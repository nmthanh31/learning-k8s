Tạo 4 loại lỗi — đọc hiểu từng cái

Containerd hay kubelet? # Lỗi 2: Command sai → CrashLoopBackOff kubectl run err2 --image=busybox -- /bin/lenh-khong-co kubectl describe pod err2 kubectl logs err2 # Exit Code 127 nghĩa là gì? (command not found) # Lỗi 3: Thoát ngay lập tức → Completed hoặc Error kubectl run err3 --image=busybox -- /bin/sh -c "echo hello && exit 0" # Tại sao pod này không Running? Đọc Exit Codes — bảng tra cứu sống
Exit codes không phải để nhớ — phải hiểu logic để suy ra được khi gặp lần đầu.
Exit codes quan trọng nhất
Exit 0 — hoàn thành thành công (Completed)
Exit 1 — lỗi chung của application
Exit 127 — command not found (CrashLoopBackOff thường gặp)
Exit 137 — bị kill bằng SIGKILL (128+9). Thường = OOMKilled
Exit 143 — bị kill bằng SIGTERM (128+15). K8s graceful shutdown
Mental Model: Exit Code = 128 + Signal Number
Linux signals: SIGKILL=9, SIGTERM=15. Nếu thấy exit code >128, trừ đi 128 = số signal. Không cần nhớ bảng — chỉ cần hiểu logic này.
Thứ 5 kubectl như một detective — lệnh investigate 1.5 giờ · kubectl mastery ▾
90 phút
Tập dùng kubectl để "đọc cluster" — không phải chỉ tạo/xóa
Phần lớn người mới chỉ biết apply và delete. CKA đòi hỏi bạn dùng kubectl để điều tra.
# === NHÓM 1: Lấy thông tin sâu hơn === kubectl get pod mypod -o yaml # full spec + status kubectl get pod mypod -o json # JSON format kubectl get pod mypod -o jsonpath='{.status.podIP}' # chỉ lấy IP kubectl get pod mypod -o jsonpath='{.spec.containers[*].name}' # tên containers kubectl get pods -o wide # xem pod đang ở node nào kubectl get pods --show-labels # xem labels của pods # === NHÓM 2: Events — "nhật ký thật sự" === kubectl get events --sort-by=.lastTimestamp # events mới nhất cuối kubectl get events -n default --field-selector involvedObject.name=mypod # === NHÓM 3: Logs === kubectl logs mypod # log hiện tại kubectl logs mypod --previous # log lần chạy TRƯỚC (sau crash) kubectl logs mypod -f # follow realtime kubectl logs mypod --since=5m # chỉ 5 phút gần nhất # === NHÓM 4: Exec vào pod === kubectl exec -it mypod -- bash kubectl exec mypod -- cat /etc/nginx/nginx.conf # không cần -it kubectl exec mypod -- env | grep HOSTNAME # xem biến môi trường
Thực hành điều tra — tự đặt câu hỏi
Tạo 3 pods, dùng -o jsonpath để in ra IP của tất cả pods cùng lúc
Gây crash 1 pod (dùng lệnh sai), sau đó dùng --previous để đọc log trước crash
Exec vào pod nginx đang chạy, đọc file /etc/hosts — có gì trong đó? Tại sao?
Thứ 6 YAML không phải để copy — để đọc và viết 1.5 giờ · YAML fluency ▾
45 phút
Phân tích YAML Pod từng field
Dùng lệnh này để xem YAML "thật" của pod đang chạy — không phải template copy từ Google.
kubectl get pod mypod -o yaml > mypod-full.yaml # Mở file, đọc từng dòng, tự giải thích # Đặc biệt chú ý: spec vs status # spec = bạn muốn gì (desired) # status = hiện thực đang là gì (actual)
Các field cần hiểu, không chỉ biết
spec.containers[].resources — requests vs limits, đơn vị CPU "100m" = 0.1 CPU
spec.volumes và spec.containers[].volumeMounts — phải match bằng tên
status.conditions — 4 conditions: Initialized, Ready, ContainersReady, PodScheduled
metadata.labels vs spec.selector trong Deployment — đây là cơ chế "nối" mọi thứ
45 phút
Viết YAML từ đầu — không Google
Mục tiêu không phải viết đúng ngay lần đầu. Mục tiêu là biết chỗ nào mình còn thiếu.
# Thử viết từ đầu: # Pod có: 1 container nginx, resource limit cpu=200m mem=128Mi, # env var APP_ENV=production, mount 1 emptyDir vào /tmp/data vim my-pod.yaml kubectl apply -f my-pod.yaml # Xem lỗi nếu có, đọc hiểu lỗi, fix
Cách dùng --dry-run đúng cách
Dùng kubectl run --dry-run=client -o yaml để sinh template, sau đó hiểu từng field rồi edit. Không phải copy blindly — sinh ra → đọc → sửa theo ý mình → apply.

Rolling update — quan sát từng bước
# Mở 2 terminal: terminal 1 watch, terminal 2 execute # Terminal 1: kubectl get pod -w # Terminal 2: kubectl set image deploy/web nginx=nginx:1.25 # Quan sát: pods cũ Terminating, pods mới ContainerCreating # Đây là Rolling Update: không down toàn bộ cùng lúc kubectl rollout history deploy/web # xem lịch sử kubectl rollout undo deploy/web # rollback về trước kubectl rollout status deploy/web # xem tiến trình rollout
Mental Model: Deployment = Time Machine cho Pods
Deployment giữ lịch sử các ReplicaSet (mỗi RS = 1 version). Rollback = chuyển về RS cũ. Đây là lý do tại sao cần 3 layer — RS không có khái niệm history, Deployment có.
Thứ 3 Labels & Selectors — cơ chế kết nối MỌI THỨ trong K8s 1.5 giờ · the glue of K8s ▾
90 phút
Labels không phải metadata — labels là cơ chế binding
Đây là concept quan trọng nhất trong K8s mà người copy-paste hay bỏ qua. Mọi thứ trong K8s kết nối với nhau qua labels + selectors.
# Tạo pods với labels khác nhau kubectl run web1 --image=nginx --labels=app=web,tier=frontend,env=prod kubectl run web2 --image=nginx --labels=app=web,tier=frontend,env=staging kubectl run db1 --image=postgres --labels=app=db,tier=backend,env=prod # Filter bằng selector kubectl get pods -l app=web # app=web kubectl get pods -l app=web,env=prod # AND condition kubectl get pods -l 'env in (prod,staging)' # OR condition kubectl get pods -l env!=staging # NOT condition # Service kết nối pods qua label selector kubectl expose pod web1 --port=80 --name=web-svc kubectl get svc web-svc -o yaml | grep -A3 selector # selector: app=web → Service sẽ route đến MỌI pod có label app=web # Xem Endpoints — đây là danh sách IP thực của pods kubectl get endpoints web-svc # Thêm label app=web vào db1 → nó sẽ xuất hiện trong Endpoints! kubectl label pod db1 app=web kubectl get endpoints web-svc # bây giờ có 2 IPs
Bài học từ lab này
Service không biết pod nào là "đúng" — nó chỉ route đến bất kỳ pod nào có label match. Đây là bug phổ biến nhất trong K8s production.
Deployment selector vs Service selector — đây là 2 selectors riêng biệt, có thể khác nhau.
Tại sao khi debug service không hoạt động, bước đầu tiên luôn là: kubectl get endpoints?
Thứ 4 Service — từ ClusterIP đến DNS, hiểu chuỗi hoàn chỉnh 1.5 giờ · service networking ▾
90 phút
Trace một request từ đầu đến cuối
Tạo web app + service, sau đó trace đường đi của một HTTP request từ bên trong cluster.
# Setup kubectl create deploy backend --image=nginx --replicas=2 kubectl expose deploy backend --port=80 --name=backend-svc # Xem "bản đồ" kết nối kubectl get svc backend-svc # CLUSTER-IP: 10.x.x.x kubectl get endpoints backend-svc # Pod IPs thực # Test từ pod khác — trace DNS → ClusterIP → Pod kubectl run client --image=busybox:1.28 --rm -it -- sh # Bên trong pod client: # Bước 1: DNS lookup nslookup backend-svc nslookup backend-svc.default.svc.cluster.local # Bước 2: HTTP request qua service name wget -qO- backend-svc # Bước 3: HTTP request qua ClusterIP trực tiếp wget -qO- 10.x.x.x # thay bằng IP thực # Bước 4: HTTP request thẳng vào Pod IP wget -qO- POD_IP # thay bằng IP pod thực
Mental Model: Request flow trong K8s
Service name → CoreDNS resolve → ClusterIP → kube-proxy iptables → Pod IP (random load balance). ClusterIP là virtual IP — không có process nào "lắng nghe" ở đó. kube-proxy dùng iptables DNAT rule để redirect.

Thứ 6 Storage cơ bản — tại sao Pod cần PersistentVolume? 1.5 giờ · storage fundamentals ▾
40 phút
Chứng minh tại sao cần persistent storage
# Bước 1: Tạo pod, ghi dữ liệu vào container filesystem kubectl run testpod --image=busybox -- sleep 3600 kubectl exec testpod -- sh -c "echo 'important data' > /data/file.txt" kubectl exec testpod -- cat /data/file.txt # OK # Bước 2: Xóa pod và tạo lại kubectl delete pod testpod kubectl run testpod --image=busybox -- sleep 3600 kubectl exec testpod -- cat /data/file.txt # FILE KHÔNG CÒN! # → Đây là lý do cần PersistentVolume
50 phút
PV + PVC — hiểu mô hình 2 layer
# Tạo PersistentVolume (admin làm) cat <<EOF | kubectl apply -f - apiVersion: v1 kind: PersistentVolume metadata: name: my-pv spec: capacity: storage: 1Gi accessModes: [ReadWriteOnce] hostPath: path: /data/my-pv persistentVolumeReclaimPolicy: Retain EOF # Tạo PVC (developer làm — không biết về PV cụ thể) kubectl create -f - <<EOF apiVersion: v1 kind: PersistentVolumeClaim metadata: name: my-pvc spec: accessModes: [ReadWriteOnce] resources: requests: storage: 500Mi EOF kubectl get pv,pvc # STATUS: Bound
Mental Model: Tại sao cần 2 layer PV/PVC?
PV = kho vật lý (admin quản lý, biết về hardware, NFS, cloud disk...). PVC = yêu cầu của developer (chỉ cần biết "tôi cần 500Mi ReadWriteOnce"). Sự phân tách này cho phép developer không cần biết infrastructure đang dùng gì.

Thứ 2 RBAC — K8s là một hệ thống có xác thực, không phải "free-for-all" 1.5 giờ · security mindset ▾
90 phút
Hiểu RBAC từ nguyên tắc, không từ YAML
Trước khi viết YAML, hiểu câu hỏi: "Ai (Subject) được làm gì (Verb) với cái gì (Resource)?"
# Tạo ServiceAccount kubectl create sa reader-sa -n default # Tạo Role: được phép get/list pods kubectl create role pod-reader \ --verb=get,list,watch \ --resource=pods # Bind SA với Role kubectl create rolebinding reader-bind \ --role=pod-reader \ --serviceaccount=default:reader-sa # ⭐ Verify bằng can-i — đây là lệnh CKA hay dùng nhất kubectl auth can-i list pods \ --as=system:serviceaccount:default:reader-sa # → yes kubectl auth can-i delete pods \ --as=system:serviceaccount:default:reader-sa # → no (chưa được cấp quyền delete) kubectl auth can-i list nodes \ --as=system:serviceaccount:default:reader-sa # → no (Role chỉ áp dụng trong namespace, không phải cluster-wide)
Câu hỏi phân biệt Role vs ClusterRole
Tại sao cần ClusterRole? Có những resource nào không thuộc namespace (nodes, pv, namespaces...)?
Có thể dùng ClusterRole + RoleBinding (không phải ClusterRoleBinding) không? Khi nào hữu ích?
Mọi pod đều có ServiceAccount mặc định là "default" — SA này có quyền gì? Thử kubectl auth can-i list pods --as=system:serviceaccount:default:default
Thứ 3 Reconciliation Loop — trái tim của K8s 1.5 giờ · how K8s really works ▾
90 phút
K8s không "làm theo lệnh" — K8s "đạt trạng thái mong muốn"
Đây là concept khó nhất nhưng quan trọng nhất để hiểu K8s. Một khi hiểu điều này, mọi thứ khác sẽ tự nhiên có logic.
# Thí nghiệm 1: ReplicaSet reconciliation kubectl create deploy demo --image=nginx --replicas=3 kubectl get pods -l app=demo # 3 pods # Xóa 1 pod thủ công kubectl delete pod demo-xxxx-yyyy kubectl get pods -l app=demo # vẫn 3 pods! (pod mới tạo) # → Ai tạo lại? ReplicaSet controller đang WATCH và RECONCILE # Thí nghiệm 2: Desired vs Actual kubectl scale deploy demo --replicas=5 # desired = 5 # K8s thấy: actual=3, desired=5 → tạo thêm 2 pods kubectl scale deploy demo --replicas=2 # desired = 2 # K8s thấy: actual=5, desired=2 → xóa 3 pods # Thí nghiệm 3: Edit trực tiếp spec.replicas kubectl edit deploy demo # thay replicas: 4 # Lưu lại → K8s scale ngay
Mental Model: Declarative vs Imperative
Bạn không nói "hãy tạo 2 pods mới". Bạn nói "trạng thái mong muốn là 5 pods". K8s liên tục so sánh desired state (trong etcd) với actual state (thực tế) và tự điều chỉnh. Đây là tại sao gọi là "declarative" — bạn khai báo kết quả, không khai báo quy trình.
Thứ 4 Debug như pro — xây dựng quy trình cá nhân 2 giờ · debug methodology ▾
120 phút
Tạo 6 lỗi khác nhau — tự debug không xem solution
Hôm nay không có "hướng dẫn debug". Bạn tự tạo lỗi, tự tìm cách debug. Đây là cách duy nhất để xây cơ bắp debug.
# Lỗi 1: Service không reach được kubectl create deploy app --image=nginx kubectl expose deploy app --port=80 --name=app-svc # Thay đổi label của deployment để KHÔNG match service selector kubectl label deploy app app=wrong-app --overwrite # → Debug: tại sao curl app-svc fail? # Lỗi 2: Pod không schedule kubectl run unschedulable --image=nginx \ --overrides='{"spec":{"nodeSelector":{"disk":"ssd-that-doesnt-exist"}}}' # → Debug: tại sao pod Pending? # Lỗi 3: Wrong env var kubectl create cm broken-cm --from-literal=DB_URL=wrong-url # Pod reference ConfigMap này → app lỗi vì sai URL # → Debug: tìm giá trị env var đang inject vào pod # Lỗi 4: Volume mount sai path # PVC mount vào /data nhưng app đọc từ /app/data # → Debug: exec vào pod, kiểm tra file system
Quy trình debug — hình thành thói quen này
kubectl get [resource] — xem trạng thái tổng quan
kubectl describe [resource] — xem Events và Conditions
kubectl logs [pod] — xem application logs
kubectl exec [pod] -- env — verify config đang inject
kubectl get endpoints — verify service routing
Thứ 5 kubectl explain — tra cứu không cần Google 1 giờ · self-sufficiency ▾

kubectl explain là docs trong terminal — dùng được trong thi
# Xem structure của bất kỳ resource kubectl explain pod kubectl explain pod.spec kubectl explain pod.spec.containers kubectl explain pod.spec.containers.livenessProbe kubectl explain pod.spec.containers.resources # Xem toàn bộ fields (recursive) kubectl explain pod --recursive | grep -i probe kubectl explain deployment --recursive | grep -i strategy # Thực hành: Viết Pod YAML với livenessProbe # CHỈ dùng kubectl explain, không Google kubectl explain pod.spec.containers.livenessProbe # → viết YAML đúng từ output này
Challenge: viết 3 YAML chỉ dùng kubectl explain
Pod với startupProbe (khác livenessProbe chỗ nào? kubectl explain để trả lời)
Deployment với podAntiAffinity (prefer không chạy 2 pods cùng node)
CronJob với concurrencyPolicy=Forbid và successfulJobsHistoryLimit=3

10 câu hỏi không được tra Google — tự chấm điểm
Làm từng câu, ghi thời gian. Mục tiêu: trả lời được 7/10, không phải 10/10.
10 câu tự kiểm tra
Tạo Pod có 2 containers chia sẻ 1 emptyDir volume. Container 1 ghi file, container 2 đọc. Viết YAML hoàn chỉnh.
Service của bạn không route traffic. Liệt kê 3 nguyên nhân phổ biến nhất và cách check từng cái.
Giải thích: khi bạn chạy kubectl apply -f, thứ tự các component xử lý request là gì?
Tạo ServiceAccount, Role cho phép chỉ get và list pods, bind cho SA đó. Viết 3 commands.
Pod exit code 137 nghĩa là gì? Nguyên nhân phổ biến và cách kiểm tra?
Sự khác nhau giữa readinessProbe và livenessProbe — khi nào dùng cái nào?
Tại sao Pod đang Running nhưng kubectl get endpoints service-name lại trả về empty?
emptyDir vs PersistentVolume — data trong emptyDir mất khi nào? Data trong PV mất khi nào?
Giải thích Reconciliation Loop. Tại sao khi xóa 1 pod trong Deployment, pod mới tự tạo?
Tìm xem Pod đang chạy trên node nào và IP của nó là bao nhiêu — 1 lệnh.
